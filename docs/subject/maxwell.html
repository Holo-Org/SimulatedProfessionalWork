Maxwell's demon

In 1867, James Clerk Maxwell imagined a creature small enough to see individual molecules. It sits at a trapdoor between two chambers of gas and does nothing but open and close the door: fast molecules to the left, slow ones to the right. No work is performed, yet one chamber grows hot and the other cold. The second law of thermodynamics, apparently, is optional.

It took eighty years to find the flaw, and the answer turned out not to be about heat at all. The demon must know which molecules are fast. It must remember. And a memory that is never erased eventually fills — while erasing it, Landauer showed, costs exactly the energy the demon thought it had saved. The demon does not break the second law. It pays for every bit.

A compressor is the same trick performed on bytes: find the order hiding inside apparent disorder, describe it more cheaply than it describes itself, and pay honestly for whatever order was never there. Every compressed file is a ledger of those payments — and the people who pay the bill, on every page load, have never been shown it.

You are going to build the demon, and then hand its ledger to the people who pay.

The user

MAXWELL is for web developers who ship JavaScript bundles compressed with gzip — still roughly half of the compressed traffic on the web.

A bundle is assembled from hundreds of sources: the developer's own files, and every library they pulled in. Browsers download it compressed, so what each source really costs a visitor is its share of the compressed bundle. That is the number a developer needs to decide what to cut, and it is the number their tools cannot give them.

Bundle analysers such as webpack-bundle-analyzer, rollup-plugin-visualizer and source-map-explorer all estimate it the same way: they compress each source on its own and add up the results. But a source's compressed cost depends on everything around it — a library compresses better next to code that repeats its patterns — so the estimate is wrong in ways nobody can see. The maintainer of source-map-explorer calls exact per-module gzip size "almost impossible".

The compressed bundle already contains the exact answer: every bit in it pays for some specific byte of the output. MAXWELL reads the real compressed stream, accounts for every bit, and follows the bundle's source map back to the source each byte came from. Its user gets:

  • the exact gzip cost of every source — not an estimate — in the terminal;
  • a report they can share: one self-contained page showing where the cost goes;
  • a smaller bundle, compressed by MAXWELL, that every browser already reads.

MAXWELL reports the exact gzip cost. A site that serves its bundles with another encoding pays a different one, and MAXWELL does not claim to know it. Say so wherever it could be misread.

What correctness means

Correctness has exactly one definition in this project, and it is not your own test suite.

  • Your decoder must correctly decompress any valid stream, including streams you did not produce.
  • Your encoder must emit streams that the reference implementation decompresses back to the original bytes, exactly.

Agreement with an independent implementation is the standard. Self-consistency is not evidence of anything: a decoder and an encoder that are wrong in the same way will agree with each other all day.

You are not asked to reproduce gzip's output byte for byte. That would require cloning another implementation's internal heuristics, and it would forbid ever producing smaller output than the reference — which means choosing matches differently from it.

Invocation

maxwell is driven by commands. Each one reads the file named on its command line, or standard input when none is given, and writes to standard output unless told otherwise.

Part 0The demon's ledger

The demon's whole problem was bookkeeping. So is yours.

This part is not about compression and it is never finished. It is what makes every other part of this project believable.

Build and dependencies

Pin everything: the compiler, the build tool and every library, at exact versions, identical on every machine that builds the project. A defence may begin with a fresh clone on an unfamiliar machine, and "it works on mine" ends the conversation badly.

Tests

  • Unit tests over the pieces: the bit reader, canonical Huffman construction, the window's copy semantics, the container, source-map decoding, and the arithmetic of attribution.
  • Integration tests over whole files, in both directions, against the reference implementation.
  • A differential harness: generate input, process it with your implementation and with at least one independent one, and assert that they agree — on random data, on pathological data, and on the corpora.
  • You must be able to show how much of your code is covered by tests.

Compression bugs are unusually good at hiding. A decoder that is wrong about one rare block type will process ninety-nine files perfectly and corrupt the hundredth. Fuzzing is not a bonus here; it is how you find out.

Documentation leads implementation

User-facing behaviour is documented before it is implemented, and the documentation is merged first. It is the specification the code must meet, not a description of whatever the code happened to do.

  • The reference — --help, the man page, the shell completions and the reference pages — comes from a single definition of the command line. What can be generated is generated and committed, and CI regenerates it and fails on any difference.
  • What cannot be generated — tutorials, how-to guides, explanations — is merged before the implementation it describes, and CI checks that it was.
  • Every user-facing feature is therefore two issues: its documentation, blocking its implementation.

Continuous integration and delivery

Automate all of the above. Every push builds the project on Linux x86-64 — the platform it is evaluated on — runs the suite, reports coverage and checks the documentation. A tag produces a working release binary without human intervention — a build that cannot be shipped is a build nobody can check.

Part 0 is mandatory at every defence. A fortnight in which the feature work stalls but the pipeline stayed green and the fuzzer ran is a fortnight you can defend. The reverse is not.

Part 1Opening the door

Read before you write. Implement a decoder for the DEFLATE format (RFC 1951) inside the gzip container (RFC 1952).

The format divides a stream into blocks, each independently typed. Build them in this order — the difficulty curve is steep and the first rung is very low:

  • Stored blocks. No compression at all: a length, its complement, and the bytes. Trivially testable, and it forces the container, the CRC32 and the framing into existence before anything hard happens.
  • Fixed Huffman blocks. The code tables are printed in the specification itself, so there is no header to parse — only a bit reader to get right, and it must read from the least significant bit upward.
  • Dynamic Huffman blocks. The tables are transmitted per block, themselves encoded with a code-length alphabet. Canonical code construction lives here.
  • The sliding window. Matches reach up to 32 KB backwards, and a match may legally overlap its own output — a distance of 1 and a length of 200 means one byte repeated two hundred times. A naïve memory copy will not do this correctly.

Errors a user can act on

Malformed input is not an edge case, it is a category: a truncated stream, an impossible code length, a distance pointing before the start of the output, a checksum or a declared size that disagrees with reality. A decoder that trusts its input is a security bug with a friendly interface.

Every failure must say where it happened — the byte, the bit and the block — why, in words its user understands, and, whenever there is one, what to do next.

Part 2Counting every bit

Now make the decoder say what it read. This part is the minimum viable product: the first time MAXWELL tells its user something their current tools can only estimate.

Keeping the books

Every bit the decoder reads pays for some specific byte of the output:

  • a literal's bits belong to its one byte;
  • a match's bits are shared across every byte it copies;
  • block headers and Huffman tables are overhead — report them as such, and never lose them.

The costs you attribute, overhead included, must add up exactly to the size of the compressed stream. That is a property, and you can test it.

Lines first

Attribute costs to the lines of the bundle before anything else. It needs nothing but the decoder, and it already answers a real question — where in this file does the cost sit? — for a bundle that comes without a source map.

Then sources

A source map (ECMA-426) records where every position of a bundle came from. Decode its mappings — Base64 VLQ — and follow each output byte back to its source.

  • Find the map on your own: a bundle names it in a comment at its end (//# sourceMappingURL=app.js.map). --map overrides it.
  • Report, for each source, its raw size next to its gzip cost, sorted by cost. A source that is large but cheap compresses well; one that is small but expensive is dense — an inlined image, a table of hashes — and is usually the one worth a look.
  • Test against bundles and maps produced by real bundlers — esbuild, Rollup or Vite, webpack — not against maps written by hand. Real ones are messier than the specification.

Part 3Showing the user

A table in a terminal answers the question for the person who asked it. Now answer it for everyone they work with.

The report

report --html writes one self-contained HTML page: no network access, no external files, nothing to install. It opens in any browser, and it can be attached to a pull request or published by CI.

  • Every source, sorted by cost, with its raw size.
  • A heat map of the bundle: where the cost sits, byte by byte, readable at a glance.
  • Nothing in it that depends on colour alone.

Your user already has tools like this: webpack-bundle-analyzer, rollup-plugin-visualizer and source-map-explorer all produce an HTML page. Study them. Yours must be at least as easy to read — and its figures are exact where theirs are estimated.

Ease of use

  • Colour that respects NO_COLOR, and turns itself off when the output is not a terminal.
  • Colour never the only carrier of meaning — in the terminal and in the heat map alike.
  • Configuration from a project file and from environment variables, with command-line flags overriding both.
  • Shell completions for bash, zsh, fish and nushell.
  • A man page, and --help for every command.
  • Errors that say where, why and what next — everywhere, not only in the decoder.

Ease of use is not a coat of paint applied at the end. A feature that is hard to discover, hard to configure, or that fails with an unreadable error is unfinished, however well it works.

Documentation

Your user reads documentation to get something done, so organise it by what they are trying to do:

  • a tutorial that takes them from a bundle to their first report;
  • how-to guides for the tasks they come back for;
  • a reference covering every command, flag, configuration key, environment variable and exit code;
  • explanations: how attribution works, and what "exact gzip cost" does and does not mean.

Publish it as a site, in English. Its home page is the place to compare MAXWELL with the tools your user already has.

Part 4Closing the door

Now emit what you have learned to read — and give your user a smaller bundle.

The encoder

  • Stored and fixed-Huffman output first. Valid, compatible, and frequently larger than the input — which is the correct and instructive result.
  • Dynamic Huffman output. Gather symbol frequencies, build optimal prefix codes under the format's length limit, and transmit the tables.
  • Match finding. LZ77 over a hash chain: index the last occurrences of each three-byte sequence and walk backwards looking for the longest useful match. This is where compression actually comes from, and where all the time goes.
  • Effort levels. -1 through -9 must mean something measurable — chain depth, when to end a block. A user choosing -1 is asking you to stop trying so hard.

Your output must be decompressed exactly by the reference implementation — not merely by your own decoder.

a block is emitted when ending it is cheaper than continuing it → the decision is yours, the format does not prescribe it → and it is worth more ratio than most people expect

Measuring it

Two axes, measured on published corpora — Canterbury for routine runs, Silesia for anything you intend to claim out loud — and never averaged:

Meeting the user where they are

  • report also accepts an uncompressed bundle, and compresses it the way the user's server does: with zlib, at the server's level, taken from the configuration or the command line. Only zlib reproduces what a zlib-based server sends; any other encoder, yours included, emits different bytes.
  • When there is a saving worth mentioning, the report says so in one line: how much smaller the bundle would be, compressed ahead of time at the highest level. nginx compresses at level 1 by default, so there usually is one. The configuration can silence it.
  • Under the name my_gzig, MAXWELL is a drop-in gzip, so the build steps that already call gzip can use it unchanged.

Bonus

None of these is required. They are the direction the project continues in, in the order they should be taken.

  • Cost budgets in CI. Fail a build when a source's cost goes over its budget. size-limit is the tool to compare with.
  • Lazy matching and level tuning. Defer a match by one byte when the next position offers a better one, and make every level earn its place on the corpora.
  • SIMD in the match finder. Compare sixteen bytes at a time when measuring a match, instead of one. It is the loop lazy matching has just tuned, and exactly what OxCaml's SIMD extensions are for.
  • Optimal parsing. Choose the division into literals and matches by global cost instead of greedily. The result is smaller than gzip -9 and still read by every decoder that exists — the technique behind Zopfli.
  • Parallel compression. Split the input into chunks, compress them in parallel — OxCaml's type system rules out data races between them — and stitch the results into one valid stream.
  • Zstandard, last. First a decoder, then an encoder. It reuses ideas you will already own — Huffman-coded literals, LZ77 sequences — and adds one genuinely new one: finite state entropy, read backwards, with three interleaved states. Implement it from the living format specification, not from the RFC, which is frozen and has known errata.
