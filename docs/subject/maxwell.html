Maxwell's demon

In 1867, James Clerk Maxwell imagined a creature small enough to see individual molecules. It sits at a trapdoor between two chambers of gas and does nothing but open and close the door: fast molecules to the left, slow ones to the right. No work is performed, yet one chamber grows hot and the other cold. The second law of thermodynamics, apparently, is optional.

It took eighty years to find the flaw, and the answer turned out not to be about heat at all. The demon must know which molecules are fast. It must remember. And a memory that is never erased eventually fills — while erasing it, Landauer showed, costs exactly the energy the demon thought it had saved. The demon does not break the second law. It pays for every bit.

You are going to build the demon.

A compressor is the same trick performed on bytes: find the order hiding inside apparent disorder, describe it more cheaply than it describes itself, and pay honestly for whatever order was never there. Do it well and a file shrinks. Do it badly and — as information theory guarantees, and as you will confirm the first time you feed your compressor its own output — it grows.

The project

The formats you will be working with are frozen. Not by their specifications, which are short and public, but by their decoders: several billion web browsers, archive utilities, package managers and image viewers that already exist, already work, and will never be updated for your benefit.

This is the constraint that makes the project interesting. You cannot invent a better format, because nothing in the world could read it. What you can do is encode better into the format that already exists — producing files that are strictly smaller, that every deployed decoder still reads without modification, and that prove the improvement with a number rather than an opinion.

So maxwell is not a clone of gzip. It is a tool that must interoperate with gzip perfectly and then beat it.

Correctness has exactly one definition in this project, and it is not your own test suite.

  • Your decoder must correctly inflate any valid stream, including streams you did not produce.
  • Your encoder must emit streams that the reference implementation decompresses back to the original bytes, exactly.

Agreement with the reference implementation is the standard. Self-consistency is not evidence of anything: a decoder and an encoder that are wrong in the same way will agree with each other all day.

You are not asked to reproduce gzip's output byte for byte. That would require cloning another implementation's internal heuristics, and it would make Part 3 impossible — beating the reference on ratio requires deliberately disagreeing with it about which matches to choose.

Part 0The demon's ledger

The demon's whole problem was bookkeeping. So is yours.

This part is not about compression and it is never finished. It is what makes every other part of this project believable.

Build and dependencies

Your toolchain must be pinned and reproducible. A defence may begin with a fresh clone on an unfamiliar machine, and "it works on mine" ends the conversation badly. State which compiler version you target and make that statement enforceable rather than aspirational.

Tests

  • Unit tests over the pieces: bit reader, canonical Huffman construction, window copy semantics, container headers.
  • Integration tests over whole files, in both directions, against the reference implementation.
  • A differential harness: generate input, process it with your implementation, process it with the reference, and assert the results agree. Run it on random data, on pathological data, and on the corpora.
  • You must be able to show how much of your code is covered by tests.

Compression bugs are unusually good at hiding. A decoder that is wrong about one rare block type will process ninety-nine files perfectly and corrupt the hundredth. Fuzzing is not a bonus here; it is how you find out.

Continuous integration and delivery

Automate all of the above. Every push must build the project, run the suite, and report coverage. Your pipeline must additionally produce a working release binary without human intervention — a build that cannot be shipped is a build nobody can check.

Part 0 is mandatory at every defence. A fortnight in which the feature work stalls but the pipeline stayed green and the fuzzer ran is a fortnight you can defend. The reverse is not.

Part 1Opening the door

Read before you write. Implement a decoder for the DEFLATE format (RFC 1951) inside the gzip container (RFC 1952).

The format divides a stream into blocks, each independently typed. Build them in this order — the difficulty curve is steep and the first rung is very low:

  • Stored blocks. No compression at all: a length, its complement, and the bytes. Trivially testable, and it forces the container, the CRC32 and the framing into existence before anything hard happens.
  • Fixed Huffman blocks. The code tables are printed in the specification itself, so there is no header to parse — only a bit reader to get right, and it must read from the least significant bit upward.
  • Dynamic Huffman blocks. The tables are transmitted per block, themselves encoded with a code-length alphabet. Canonical code construction lives here.
  • The sliding window. Matches reach up to 32 KB backwards, and a match may legally overlap its own output — a distance of 1 and a length of 200 means one byte repeated two hundred times. Naïve memcpy will not do this correctly.

Malformed input is not an edge case, it is a category. A decoder that trusts its input is a security bug with a friendly interface. Decide early what your program does with a truncated stream, an impossible code length, a distance pointing before the start of output, or a declared size that disagrees with reality.

Part 2Closing it again

Now emit what you have learned to read. Your output must be decompressed correctly by the reference implementation, not merely by your own decoder.

  • Stored and fixed-Huffman output first. Valid, compatible, and frequently larger than the input — which is the correct and instructive result.
  • Dynamic Huffman output. Gather symbol frequencies, build optimal prefix codes under the format's length limit, and transmit the tables.
  • Match finding. LZ77 over a hash chain: index the last occurrences of each three-byte sequence and walk backwards looking for the longest useful match. This is where compression actually comes from, and where all the time goes.
  • Effort levels. -1 through -9 must mean something measurable — chain depth, lazy matching, when to end a block. A user choosing -1 is asking you to stop trying so hard.
a block is emitted when ending it is cheaper than continuing it → the decision is yours, the format does not prescribe it → and it is worth more ratio than most people expect

Throughput

Profile before optimising, and let the profile choose the target. Vectorisation is available to you where the work is genuinely parallel, but note that most of a compressor's time is spent in a data-dependent search that resists it — cache behaviour in the match finder is usually worth more than instruction width, and the only way to know is to measure.

Ratio

Greedy match selection is not optimal. Taking the longest match available at each position can force a worse choice immediately afterwards, and the cost of a match depends on the Huffman code that has not been built yet. Choosing the parse by global cost instead of local cost yields a meaningfully smaller file in the same format, readable by every decoder that already exists.

This is the result the project exists to produce: a file that any deployed tool reads without modification, that is smaller than that tool could have made it. State the improvement as a percentage, on a published corpus, against a named version of the reference implementation.

Bonus

The tracks below are not required. They are the direction the project continues in, and they are ordered by dependency rather than by difficulty.

  • More containers. Raw DEFLATE and the zlib wrapper (RFC 1950). Cheap, and it widens what you can be tested against.
  • A modern decoder. Zstandard reuses ideas you will already own — its literals are Huffman-coded and its sequences are LZ77 triples — and adds one genuinely new one: finite state entropy, read backwards, with three interleaved states. Implement from the living format specification, not from the RFC, which is frozen and has known errata.
  • A modern encoder. Zig's standard library can read Zstandard and cannot write it. That is the gap this project is ultimately pointed at.
  • Parallelism. Independent blocks compress independently. Decompression is far less willing.
  • Dictionaries. Priming the window with sample data, for corpora of many small similar files.
